The third release candidate for v0.12.0 lets cause chat compare a failure with the last passing run, keeps Fix previews available through transient GitHub failures, makes Fix pull request bodies clearer, and fixes the detail page side rail offset.

These notes cover changes since v0.12.0-rc.2. The critique contract remains at version 18, so upgrading does not invalidate AI analysis caches. There are no breaking changes. This is a pre-release and does not advance the stable `v0` alias. Existing consumers keep their own refs; to test this candidate, pin the deployment explicitly to v0.12.0-rc.3.

## Changed

- **Cause chat can compare with the last passing run.** New cause conversations bind the last fully passing retained run before the cause's first failing build as baseline evidence, even when its dashboard JUnit is truncated, and offer "What changed since the last passing run?" The chat compares job inputs, commits, rendered resources, and node OS image and kernel before logs. The baseline does not change cause membership, recovery status, or Fix targets. Previously, comparison evidence only included a later completed run.
- **Fix pull request bodies are clearer.** Generated Fix PRs link failed builds to Prow when a URL is recorded and include a footer disclosing that the change was generated by an AI coding agent in Aster and reviewed by a maintainer before opening. Verification results, investigation warnings, and backport suggestions appear as plain text instead of GitHub callouts. The footer's build links, verification and backport information, and AI disclosure stay outside the template-filled text, so template filling cannot remove them.

## Fixed

- **Fix confirmation keeps valid previews when GitHub source checks fail.** Fix source checks previously made unauthenticated GitHub requests unless `SOURCE_INVESTIGATION_GITHUB_TOKEN` was set, so they could hit the shared 60-per-hour rate limit, and any failure deleted the preview as if its evidence had changed. Source checks now use the configured `GITHUB_READ_TOKEN`, `BOT_TOKEN`, or `GITHUB_TOKEN` by default, and failures before any write keep the preview for retry. Actual evidence or source base changes still require a new preview.
- **Fix confirmation failures are diagnosable.** Confirmation failures log a sanitized operator reason, and GitHub write errors name the failing operation and repository. A 404 when creating a commit or branch hints at token access or the `workflow` scope. In fork mode, a classic PAT needs the `workflow` scope when the upstream base contains workflow changes the fork lacks. See [Fix PRs](../docs/fix-prs.md#identity-cla-and-the-token).
- **The detail page side rail no longer leaves an 80px gap.** Job and test detail side rails stick 16px from the top on large screens and stop sticking on viewports shorter than 800px so their bottom links stay reachable.
